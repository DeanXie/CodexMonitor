# Phase 2.4.2 Cross-View Deletion Reconciliation Design

## Goal

Make a confirmed Codex `thread/delete` permanently retire the selected canonical Thread and every descendant supported by confirmed parent/child identity evidence from CodexMonitor's Global Source lifecycle. Retirement must survive process crashes and restart, remove stale watcher/checkpoint state, prevent rollout or historical replay from resurrecting the deleted identity, and clear CodexMonitor-owned view caches without modifying Codex Desktop private indexes.

## Scope

This phase adds deletion reconciliation around the existing official `thread/delete` operation. It does not change Phase 1 Runtime semantics, SourceEnvelope authority rules, token reconciliation, Desktop private state, or the official server deletion behavior.

The lifecycle is:

```text
thread/delete confirmed
→ persist deletion tombstone
→ retire SourceAuthorityRegistry identities
→ retire active/restored Rollout Watcher sources
→ rewrite watcher checkpoint
→ publish canonical snapshot
→ mark deletion reconciliation completed
```

This is a crash-safe reconciliation sequence, not an ACID transaction across unrelated stores. The persisted tombstone is the recovery anchor. Every later step is idempotent and can be replayed after restart.

## Deletion Identity and Evidence

Deletion is keyed only by canonical Codex identity:

```text
CodexThreadKey = (codexHomeIdentity, fullThreadId)
```

Titles, UI position, workspace ordering, rollout path adjacency, filename similarity, and user-visible labels are never identity evidence.

The requested descendant closure is computed only from confirmed parent/child relationships already held by the Runtime assignment evidence or Global Source canonical identity evidence. The backend stores the exact requested and confirmed identities. A Thread not present in that evidence closure is not retired as a descendant.

## Tombstone Contract

The shared Global Source Core owns a persisted deletion document. Each operation contains:

```text
DeletionTombstone
├── monitorDeleteOperationId: UUID
├── upstreamRequestId: null
├── rootThreadKey: CodexThreadKey
├── descendantThreadKeys: CodexThreadKey[]
├── deletedAtMs: i64
├── deleteResponseConfirmed: bool
├── threadDeletedConfirmations: fullThreadId[]
├── postDeleteThreadListAbsent: fullThreadId[]
├── retiredSourceFiles: SourceFileIdentity[]
├── reconciliationState: pending | completed
└── desktopReconciliation: unknown | refreshPending | reconciled
```

`monitorDeleteOperationId` is generated by CodexMonitor before invoking the official delete command and is only a local operation correlation UUID. It is not an app-server JSON-RPC request ID. `upstreamRequestId` remains `null` until a future protocol surface exposes a real upstream request identifier; it must never be inferred or synthesized.

The tombstone file is stored under CodexMonitor app data beside the rollout watcher checkpoint. It is written atomically using a temporary file, `fsync`, and rename. The document is versioned and preserves completed tombstones because they are required to reject later stale discovery and historical replay.

No tombstone is created when `thread/delete` fails or is rejected.

## Backend Delete Orchestration

The frontend supplies the selected root fullThreadId, confirmed descendant fullThreadIds, and a generated `monitorDeleteOperationId`. The backend resolves the workspace's canonical CODEX_HOME identity and invokes the existing official `thread/delete` command.

After a successful response, the backend submits a deletion reconciliation command to the unique Global Rollout Watch Service. The command contains the canonical root key, confirmed descendant keys, operation UUID, deletion timestamp, and `deleteResponseConfirmed=true`.

The command first persists a `pending` tombstone. Only after persistence succeeds may it mutate Registry or Watcher state. If tombstone persistence fails, the official server deletion remains successful but the backend returns a reconciliation error and retains enough operation information in diagnostics for recovery; it must not pretend Global Source cleanup completed.

`thread/deleted` notifications are forwarded to the same service as independent confirmation evidence. Notifications may arrive before or after the delete response and may be emitted per descendant or only for a subset. They improve the tombstone evidence but are not assumed to be the sole cascade signal.

Post-delete `thread/list` reconciliation uses fullThreadId equality. Absence evidence is recorded per scoped identity only after the relevant server list result no longer contains that fullThreadId. Titles are ignored. The tombstone can reach reconciliation `completed` after all local retirement/checkpoint/snapshot steps succeed even while Desktop remains `refreshPending`; Desktop reconciliation is a separate consumer-view status.

## Source Authority Registry Retirement

`SourceAuthorityRegistry` gains a tombstoned-key set and idempotent retirement operations.

Retiring a key removes its canonical lanes, turns, parent/agent metadata, and observation keys associated with those lanes. The registry snapshot excludes retired identities.

All ingest paths check the tombstoned-key set before identity observation or lane mutation:

- app-server LIVE ingest;
- rollout NEAR LIVE ingest;
- historical ingest;
- duplicate/retry batch ingest;
- health-only watcher updates.

An observation for a tombstoned fullThreadId is rejected as retired and cannot recreate a canonical Thread. A different fullThreadId is a new identity and is unaffected, even when its title matches the deleted Thread.

## Rollout Watcher Retirement

The watcher applies retirement to three locations:

1. Active watched sources whose adapter owner key is retired are removed immediately.
2. Restored checkpoint entries whose adapter owner key is retired are discarded before discovery.
3. Discovered or replayed sources are checked against tombstones before Registry ingest. If their confirmed owner key is retired, the source is retired and its file identity is attached to the tombstone instead of being published.

Known retired `SourceFileIdentity` values are skipped during later filesystem notification and periodic discovery. This prevents repeated reads of a deleted rollout path and stops new `os error 2` retries after retirement.

If a source path disappears before a delete command is received, reconciliation removes the missing watched source once its canonical owner is tombstoned. A missing non-tombstoned source keeps the existing retry/reconciliation behavior; deletion logic must not silently classify unrelated I/O failures as deletion.

## Checkpoint Reconciliation

After active/restored source retirement, the watcher rewrites its existing checkpoint from the remaining source set. No entry whose adapter owner key or source file identity is tombstoned may be serialized.

On process startup:

1. Load deletion tombstones before the watcher checkpoint.
2. Reapply every `pending` and `completed` tombstone to the restored checkpoint entries.
3. Start discovery with tombstone filtering already active.
4. Re-run idempotent Registry/Watcher/checkpoint cleanup for `pending` operations.
5. Publish the clean canonical snapshot.
6. Mark operations `completed` after all local reconciliation steps succeed.

A crash at any point after tombstone persistence therefore cannot resurrect the deleted canonical identity from an old checkpoint or rollout file.

## Snapshot and Diagnostic Contract

Canonical snapshot revision advances when retirement changes the published Thread set. The existing Global Source View Store consumes the resulting immutable snapshot and removes the deleted Session without a special fake Runtime event.

The diagnostic surface records only deletion metadata needed for reconciliation:

- `monitorDeleteOperationId`;
- root and descendant fullThreadIds;
- tombstone persistence outcome;
- Registry retirement count;
- watcher source retirement count;
- checkpoint rewrite outcome;
- snapshot publication revision;
- reconciliation state;
- Desktop reconciliation state.

No prompt, reasoning content, Desktop private database content, or inferred upstream request ID is recorded.

## CodexMonitor View and Cache Cleanup

After the backend confirms the official delete and accepts the tombstone operation, the existing frontend deletion flow clears:

- Sidebar and Recent Threads reducer entries;
- active Thread selection and Current Session identity when the current Chat was deleted;
- Agent Monitor Session through the revised Global Source snapshot;
- the existing Phase 1 live-tree exclusion set without changing Runtime state semantics;
- drafts and attached images already covered by the current deletion flow;
- `codexmonitor.threadLastUserActivity` entries;
- pinned Thread entries;
- custom Thread names;
- per-Thread Codex parameter overrides;
- detached review links.

Cleanup is scoped to the selected workspace/fullThreadId identities. Other Threads and the Workspace remain unchanged. The frontend still performs its normal server thread-list refresh; Archive behavior remains separate.

## Desktop Reconciliation State

Desktop is an independent consumer view and is not a Source of Truth for Thread existence.

The tombstone stores one of:

- `unknown`: no Desktop consumer evidence has been evaluated;
- `refreshPending`: server deletion is confirmed, but Desktop has not yet been observed without the fullThreadId;
- `reconciled`: a later Desktop list/sidebar observation identified by exact fullThreadId no longer contains the deleted identity.

This phase sets successful deletions to `refreshPending`. It exposes an idempotent future update path for exact-ID Desktop absence evidence but does not read, write, rebuild, or delete:

- `session_index.jsonl`;
- `.codex-global-state.json`;
- `state_5.sqlite`;
- Desktop private cache or sidebar state.

## Failure and Ordering Rules

- App-server delete failure: return the error, retain all current UI/source state, create no tombstone.
- Duplicate delete confirmation: reuse the same operation when the operation UUID matches; retirement remains idempotent.
- `thread/deleted` before delete response: retain confirmation evidence until the operation is persisted, then merge it.
- `thread/deleted` without a known local delete operation: remove the frontend Thread as today and record confirmation evidence, but do not invent descendant closure or a local deletion operation.
- Tombstone persisted, later step fails: leave reconciliation `pending`; startup or the next service reconciliation retries the remaining steps.
- Checkpoint rewrite failure: do not mark reconciliation completed; tombstone filtering still blocks Registry ingest and startup recovery retries the rewrite.
- Snapshot emission failure: Registry remains retired; the next snapshot read/event reconciliation exposes the clean state.
- Same title with a new fullThreadId: accepted as a separate Thread.

## TDD Coverage

Backend shared-core tests must prove:

- failed official deletion creates no tombstone;
- successful deletion persists `monitorDeleteOperationId` and `upstreamRequestId=null`;
- confirmed descendant closure retires Main and descendants only;
- Registry removes retired canonical Threads and rejects LIVE, NEAR LIVE, and HISTORICAL resurrection;
- duplicate retirement and duplicate notifications are idempotent;
- active and restored watcher sources are removed;
- checkpoint no longer contains retired owners or source files;
- stale rollout discovery cannot reactivate a tombstoned Thread;
- a different fullThreadId with the same title remains observable;
- restart from a pending tombstone completes reconciliation before discovery publication;
- a deleted/missing rollout path stops producing new `os error 2` failures;
- unrelated Threads and sources remain unchanged;
- Desktop state transitions only by exact fullThreadId evidence.

Frontend tests must prove:

- successful deletion removes Sidebar/Recent Threads/Current Session projection;
- Agent Monitor Global Source Session disappears after the canonical snapshot update;
- Monitor-owned localStorage entries for Main and confirmed descendants are removed;
- unrelated cache entries remain;
- server deletion failure leaves local state and cache unchanged;
- Archive behavior remains unchanged.

## Non-Goals

- No Codex Desktop private index, SQLite, cache, or sidebar mutation.
- No Codex index reconstruction.
- No Phase 1 Runtime state-machine change.
- No SourceEnvelope contract or Token authority change.
- No second rollout watcher.
- No Desktop Adapter implementation.
- No Phase 3 work.

## Phase Exit Criteria

Phase 2.4.2 may be marked PASS only when automated tests prove the crash-safe tombstone/recovery path, Registry and Watcher retirement, checkpoint cleanup, cache cleanup, cascade isolation, failure behavior, and anti-resurrection rules. A focused runtime diagnostic must additionally show that the `os error 2` count for a retired deleted rollout path stops increasing after reconciliation.

After PASS, Phase 2.5 can resume at its frozen starting point: `Desktop Compacted Child Rollout — File Owner / Replay Guard` Formal TDD.
